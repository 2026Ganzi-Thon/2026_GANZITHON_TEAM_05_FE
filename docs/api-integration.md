# API 연동 상태

2026-11-19 기준. 프런트 브랜치: `feat/api-integration`.

기준 자료는 전달받은 「Letit API 상세 명세서 v1.0 (26개 · 프론트 공유용)」 PDF와 백엔드 저장소의 실제 OpenAPI·스키마입니다. PDF의 지침은 계약을 이해하는 참고 자료로 사용했고, 카카오맵 전환과 위치 권한 요청은 사용자가 별도로 승인한 범위입니다.

## 구현과 확인 범위

프런트의 26개 요청은 `src/api/endpoints.ts`에 모았으며 모두 화면 이벤트나 서버 조회 훅에서 호출합니다. 프런트 요청 연결 누락은 없습니다. API 모드에서는 성공 데이터를 목업으로 대체하지 않습니다. 아래의 '명세 재현'은 실제 서버 전체 연동 검증 완료를 뜻하지 않습니다. 백엔드 저장소는 원래 main으로 원복했고, 이후 작업에서는 코드·브랜치·설정을 변경하지 않고 PR 소스만 읽었습니다.

| 기능                                                            | API 수 | 프런트 | 검증 방법                                            |
| --------------------------------------------------------------- | -----: | ------ | ---------------------------------------------------- |
| 회원가입·로그인                                                 |      2 | 연결   | 로컬 실제 FastAPI + 브라우저                         |

백엔드 `main`에는 인증·기본값 4개가 등록되어 있습니다. 이후 올라온 [백엔드 PR #1](https://github.com/2026Ganzi-Thon/2026_GANZITHON_TEAM_05_BE/pull/1), `feat/recommendations-places`의 `50044f9`를 별도 8001 포트와 SQLite 테스트 DB로 실행했습니다. 이 브랜치에는 총 16개 API가 등록되어 있고, 인증·기본값·미션 15개와 실제 Kakao Local 장소 검색 1개를 프런트 요청 코드로 검증했습니다. 장소 검색은 합성 좌표 주변 15개 결과를 반환했습니다. Supabase와 실제 Upstage AI 추천은 검증하지 않았으며, AI 키가 없는 로컬에서는 서버의 `fallbackUsed: true` 예비 추천으로 테스트했습니다. 공동 DB·실사용자 기록은 변경하지 않았습니다. 이 백엔드 PR은 확인 시점에 아직 main에 병합되지 않았습니다.

이후 [백엔드 PR #2](https://github.com/2026Ganzi-Thon/2026_GANZITHON_TEAM_05_BE/pull/2), `feature/a-records-collection`의 `80003d9`에 휴식·후기·성찰·아카이브·도감 10개가 추가된 것을 확인했습니다. 구현 자체는 두 PR에 모두 존재합니다. PR #2는 소스와 응답 형식을 읽어 프런트를 맞췄고, 실제 통합 서버 검증은 아직 하지 않았습니다. 두 PR 병합과 완료→달력·꽃 갱신 연결은 백엔드 담당자 범위입니다.

현재 프런트의 기본 로컬 API 주소 8000은 기존 main 서버(4개 API)를 가리킵니다. 앞서 사용한 PR 검증 전용 8001 서버는 원복 시 중지했습니다. 백엔드 담당자가 전체 26개를 등록한 서버 주소를 제공해야 실제 전체 흐름을 검증할 수 있습니다. 현재 main에서 제공하지 않는 API는 오류·재시도를 표시합니다.

## 새 백엔드 PR에 맞춘 응답 보완

- 예비 추천의 실제 필드 `fallbackUsed`를 화면의 예비 미션 안내로 연결합니다. 추천 제외 UUID는 서버 제한인 최근 50개까지만 보냅니다.
- 한국어 상황 선택을 `weather/closed/crowded/low_energy/cost/other`로 변환하여 대체 추천의 422 오류를 수정했습니다.
- PATCH 응답에 완료·남은 개수가 없어도 반환된 UUID 목록으로 표시 개수를 계산합니다.
- 이어하기 목록에 빠진 시작일·개수는 개별 미션 상세 GET으로 보완합니다.
- 장소 상세가 ID만 반환하고 이름·주소·좌표·거리가 null인 경우 화면이 중단되지 않게 처리합니다. 같은 실행에서 검색한 장소와 ID가 같으면 그 조회 결과를 재사용하고, 없으면 정보 없음으로 표시합니다. 서버 스냅샷 저장이 완료된 것은 아닙니다.

## 기록·성찰·도감 PR #2 응답 보완

- 아카이브 `endedAt: null`을 '기록 없음'으로 표시합니다. 종료하지 않은 미션에 1970년 1월 1일을 표시하지 않습니다.
- SQLite에서 반환한 시간대 없는 ISO 시각은 백엔드의 UTC 저장 규칙에 맞춰 해석합니다. 날짜 전용 값과 이미 시간대가 있는 시각은 유지합니다.
- 홈의 완료 횟수는 summary의 미션 건수를 사용합니다. 성찰의 '일' 단위는 calendar가 반환한 날짜별 상태를 세어 표시하므로 같은 날 미션을 여러 번 수행해도 일수가 늘지 않습니다.
- 꽃 확인 응답의 실제 필드(`flowerNumber/name/acquiredAt`)만 요구하도록 타입을 맞췄습니다. 확인 API 호출로 새 꽃을 클라이언트에서 생성하지 않습니다.

## 동작 규칙

- `VITE_API_BASE_URL`이 비어 있으면 기존 메모리 목업 모드입니다. 값이 있으면 API 모드로 실행하고 `/api/v1`은 중복해서 붙이지 않습니다.
- 인증 토큰은 메모리에서만 보관합니다. 명세에 refresh API가 없어 새로고침하면 재로그인합니다. 비밀번호·기분·후기·위치를 브라우저 저장소나 로그에 남기지 않습니다.
- 로그인 후 `GET /users/me/defaults`의 `onboardingCompleted`로 설문과 홈을 구분합니다. 설문 저장 실패 시 선택을 유지합니다. 계정 변경·만료 시 초안과 쿼리 캐시를 정리합니다.
- 단계는 `order`로 표시하고 `stepId` UUID 배열로 PATCH합니다. 연속 체크를 직렬화하고 저장·완료는 마지막 체크 요청을 기다립니다. POST·PUT·PATCH·DELETE는 자동 재시도하지 않습니다.
- 생성·교체 POST 후 상세 GET이 실패한 경우 받은 미션 ID로 상세만 재조회합니다. 상세 조회 실패를 이유로 같은 생성 POST를 다시 보내지 않습니다.
- 온보딩 기본값은 별도 유지합니다. 같은 실행 중에는 직전 외출의 에너지·거리·시간·예산을 재사용하고 기분·장벽은 초기화합니다.
- 장소 없는 미션은 GPS와 주변 검색을 생략합니다. 장소 미션에서 동의 버튼을 누른 뒤 GPS를 요청합니다. 거절·오류·검색 결과 없음에 재시도와 다른 미션 선택을 제공합니다.
- 주변 검색은 `placeCategory`와 에너지별 반경을 전달합니다. 장소 선택은 명세대로 카카오 `placeId` 문자열만 보냅니다. 이동 시간은 `약 N분 (추정)`입니다.
- 달력·통계·꽃은 서버 조회 결과를 표시합니다. 아카이브 삭제는 서버의 숨김 처리만 요청합니다. `claim`은 서버가 지급한 꽃을 확인하는 요청이며 클라이언트에서 지급 일수나 꽃을 생성하지 않습니다.
- 키는 `.env.local`에만 설정합니다. `.env.example`에 빈 항목을 공유합니다. `VITE_KAKAO_MAP_APP_KEY`에는 공개 JavaScript 키만 사용합니다.

## 백엔드에서 확정할 항목

1. **PR #1·#2의 서버 통합과 주소**: PR #1의 16개와 PR #2의 나머지 10개를 함께 등록한 서버 주소와 CORS가 필요합니다. 두 PR의 `main.py`가 같은 파일을 변경하므로 모든 라우터가 유지되는지 백엔드 담당자가 확인해야 합니다.
2. **장소 스냅샷**: 실제 PR #1의 생성·교체 후 상세 조회에서는 `placeId`만 저장되고 이름·주소·좌표·거리 등이 null입니다. 서버가 검색 결과를 보관하거나 ID로 재조회해 전체 장소 스냅샷을 저장해야 합니다.
3. **날짜별 상태와 꽃 갱신 연결**: PR #2가 제공하는 `docs/B_INTEGRATION.md`에는 미션 변경 API에서 기록·꽃 갱신 함수를 호출해야 한다고 명시되어 있습니다. 현재 PR #1에는 호출이 없어 서버 통합 시 백엔드 담당자의 추가 연결이 필요합니다. 프런트는 달력·꽃 결과를 임의로 생성하지 않습니다.
4. **AI 추천과 조건 준수**: 실제 AI는 Upstage 키가 있는 서버에서 별도 검증해야 합니다. 로컬 예비 추천의 에너지 0단계에는 집 밖 활동도 포함돼 있어 기획의 집 안 범위와 맞추는 서버 수정이 필요합니다.
5. **재로그인 후 직전 조건**: 명세에는 온보딩 기본값 API만 있습니다. 직전 외출 조건을 앱 재실행 이후에도 복원하려면 별도 서버 필드나 조회 경로가 필요합니다. 브라우저 영구 저장으로 대신하지 않았습니다.
6. **꽃 번호와 자동 지급**: `flowerNumber` 1~18을 Figma 에셋 번호와 동일하게 사용해야 합니다. PR #1의 완료 API는 미션 완료 상태만 저장하고 날짜별 기록·꽃 지급 갱신은 아직 없습니다. 날짜 중복 방지와 이미 얻은 꽃 유지 정책을 서버에 구현해야 합니다.
7. **중복 변경 방지**: 통신 단절 시 POST 성공 여부를 판별할 수 없는 경우를 위해 생성·교체·완료의 서버 중복 방지 정책이 필요합니다. 프런트는 변경 요청을 자동 재전송하지 않습니다.

## 로컬 검증 재현

```bash
npm test
npm run lint
npm run build
npm run format:check
```

`npm test`는 Node 기본 테스트 러너와 Vite의 TS 로더를 사용합니다. 실제 외부 서버·키 없이 26개 메서드/경로/본문/Bearer 헤더, UUID 단계, 요청 순서, 로그인 401과 세션 만료 구분, 타임아웃·취소·응답 검증, 조건 단위 변환을 검사합니다.

브라우저 검증은 로컬 실제 인증 4개와 명세 재현 응답 22개를 구분해 수행했습니다. 실제 가입·설문·재로그인, 빠른 체크·완료·후기 실패 후 재시도·꽃 확인, 위치 거부·빈 장소·지도 선택, 부분 저장·재개·중단, 대체 미션, 아카이브 페이지 추가·상세·숨김 삭제, 성찰 월 이동, 320/402/1280px 화면을 확인했습니다.

JavaScript SDK 도메인 등록과 카카오맵 사용 설정 활성화 후, 실제 카카오 SDK가 HTTP 200으로 응답하는 것을 확인했습니다. 실제 지도 타일 6개와 번호 마커 2개가 표시됐고, 카드 선택 → 마커 강조 및 지도 이동, 마커 선택 → 카드 강조가 동작했습니다. 동의 전 GPS 호출 0회·동의 후 1회를 확인했으며 브라우저 오류는 없었습니다. 지도 UI 검증은 합성 장소 목록을 사용했고, 이후 PR #1의 실제 Kakao Local 장소 검색도 별도로 HTTP 200과 15개 결과를 확인했습니다. REST 키는 Git에서 제외되는 백엔드 로컬 설정으로만 사용했습니다.

최신 프런트 계약 테스트 14개가 통과했습니다. 26개 요청 메서드·경로·인증·본문 검증 외에 PR #2의 종료일 null·UTC 시각·날짜별 집계·꽃 확인 부분 응답을 검사했습니다. 새 PR #2 응답을 재현한 브라우저 검증에서 종료일 없음, 1일 내 여러 미션의 일수 집계, 꽃 확인을 확인했고 브라우저 오류는 없었습니다. 실제 서버 호출 성공과 응답 재현 검증은 구분해서 기록합니다.
